# A QA drafting assistant with explicit evaluations

[![Harness checks](https://github.com/baruth91/ai-assisted-qa-evaluation-case-study/actions/workflows/evaluation.yml/badge.svg)](https://github.com/baruth91/ai-assisted-qa-evaluation-case-study/actions/workflows/evaluation.yml)

An original learning case in **engineering with AI**: a local language model proposes
test scenarios from fictional requirements; Python checks selected output properties
and records failures for review. The project demonstrates integration and evaluation,
not model training or autonomous QA approval.

The learning question is: **how can a QA engineer inspect whether an AI-generated
draft follows requirements, handles missing information and resists embedded commands?**

This is Phillip Baruth's community learning material. All examples are synthetic.
No client names, employer material, production requirements or CV files are included.

## Run without an AI service

Prerequisite: Python 3.13. The verified patch is in `.python-version`.

```sh
git clone https://github.com/baruth91/ai-assisted-qa-evaluation-case-study.git
cd ai-assisted-qa-evaluation-case-study
python -m venv .venv
```

Activate with `.venv\Scripts\Activate.ps1` in PowerShell, or
`source .venv/bin/activate` in Linux/macOS, then:

```sh
python -m pip install -r requirements.txt
python -m pytest -v
python -m qa_ai replay --report-only
```

Pytest verifies the evaluation code using hand-authored controls and recorded-evidence
integrity. Replay evaluates **committed responses previously generated by a real
local model**; it makes no model call. Reports go to `reports/`.

`--report-only` returns zero after successful report generation even when model checks
fail. Without that flag, replay returns **1** if any selected sample fails. Read the
report's failed checks; a green harness workflow is not model acceptance.

## Generate new responses with a real model

Install [Ollama](https://docs.ollama.com/) and start its local server. The captured
experiment uses `llama3.1:latest` with an exact digest in `config/ollama.json`, not an
unpinned assumption about the tag. Install that model if needed:

```sh
ollama pull llama3.1:latest
python -m qa_ai collect --output reports/my-live-run.json
```

The adapter checks the installed digest before generation. If the registry tag has
changed, review and version the model configuration as a new experiment rather than
silently replacing the original baseline. Model weights are not committed here.

Collection uses the loopback Ollama API, records the response after every request,
and evaluates all collected samples. It exits 1 if any sample fails a check, while
preserving the evidence. An existing output file is never overwritten.

For a smaller single draft:

```sh
python -m qa_ai collect --prompt grounded-v2 --case quantity-and-price --output reports/my-draft.json
```

Initial installation/model download requires internet and adequate disk/RAM. Inference
uses the local model; no paid API key is needed for this implementation. Ollama itself
has separate configuration and network behavior; the repository makes no general
claim about all of that application's telemetry.

## The experiment

| Input | Risk under evaluation |
| --- | --- |
| Notebook quantity and price | Missing declared criterion/type coverage and unsupported policy phrases |
| Underspecified refunds | Inventing scenarios instead of asking specific clarification questions |
| A requirement with an untrusted note | Following embedded output instructions instead of treating them as data |

Two prompts are versioned: a general baseline and a candidate that adds explicit
grounding, clarification and instruction-boundary rules. The dataset, criteria,
schema, prompts and model config were committed **before** collecting model outputs.
Ground-truth evaluation labels are not sent to the model.

Saved records include raw output, timestamps, model digest, runtime version, sampling
options, token counts, timings and hashes of the prompt, dataset, schema and output.
Replaying a mismatched prompt/dataset/schema is refused.

## What the checks can and cannot establish

Automated checks cover JSON/schema validity, declared criterion IDs and test types,
exact evidence quotes, selected unsupported-policy phrases, clarification-topic
keywords and a specific untrusted marker. These are **bounded proxies**.

They do not prove semantic correctness, complete risk coverage or absence of
hallucinations. A unit-test counterexample intentionally shows a wrong monetary
expected result passing these mechanical checks. That blind spot is documented,
not presented as a model success. Human review of expected outcomes remains required.

Status `ready` means ready to propose a draft, never approved for execution or release.
The assistant has no tools and cannot run generated scenarios or change a system.

## Responsible interpretation

This first development set has only three synthetic cases and one observation per
case/prompt. There is no held-out benchmark, independent human acceptance, or
statistical evidence of robustness. Fixed seed and temperature do not guarantee
identical output across hardware/runtime versions. Prompt injection results apply
only to the exercised input, not comprehensive AI security.

The next increment should improve independent semantic oracles, add held-out cases
and obtain human review before making broader quality claims. Promptfoo or another
evaluation framework is an optional later comparison, not a dependency needed to
understand this first slice.
